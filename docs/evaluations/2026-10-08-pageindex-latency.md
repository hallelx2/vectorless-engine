# PageIndex vs Vectorless: latency on the 3M 2018 10-K

**Date:** 2026-10-08 · **Issue:** HAL-2459 (parent HAL-2455) · **Raw data and harness:** kept with the project's internal benchmarks, not published here

> Copied into this repository on 2026-10-11 so the figure in the README has a public source. The text is unchanged apart from this note, the line above and one sentence in *Where PageIndex wins* that was written for outreach. The paths under *Reproduce* refer to the unpublished harness directory.

## Result

| per question, 18 runs each (6 questions × 3 repeats) | Vectorless | PageIndex 0.2.22 | ratio |
|---|---|---|---|
| retrieval, median | **1.70 s** | 7.05 s | 4.1× |
| retrieval, p90 | **2.15 s** | 10.63 s | 4.9× |
| full answer, median | **5.27 s** | 10.51 s | 2.0× |
| full answer, p90 | **10.15 s** | 15.84 s | 1.6× |
| retrieved pages hold the answer | **18/18** | 17/18 | |
| figure in the answer (5 numeric questions) | **15/15** | 14/15 | |
| index / ingest, ready to query | **10.5 s, 19.2 s** | 210 s, 204 s | ~14× |

Retrieval is Vectorless's server-side `timings_ms.retrieval` on `/v1/answer`. For PageIndex it is the time from the question to the last page-content tool result, the point at which the agent has its pages. Both are measured on this machine, interleaved question by question.

The retrieval models differ, so the retrieval and answer rows compare products, not models (see *Same model?*). On the one row where both systems run the same generative model end to end, Vectorless's own generative page walk, the gap narrows to 7.6 s against 10.5 s at the median, and PageIndex wins two of the six questions.

## Method

**Filing.** `3M_2018_10K.pdf`, 160 pages, sha256 `faf10c53…3934d`, generated by wkhtmltopdf.

**Questions.** The six in HAL-2459, asked in a fixed order, three repeats.

**Interleaving.** For each question, one system ran its full call, then the other. The order flipped every repeat, so machine load and provider weather fell on both systems alike. Only one request was in flight at any time.

**PageIndex.** `pip install -U pageindex` (0.2.22, identical to VectifyAI/PageIndex `1a060df`, 2026-10-08 13:17 +0800, apart from unshipped assets). Local mode, the README quickstart path: `PageIndexClient(index=…, chat=…)`, `submit_document()` with the default flash indexer, then `client.chat(question, doc_id=…, stream=True)`. The `.events` stream timestamps every tool call, tool result and the first answer token. Pages are the ones the agent asked `get_page_content` for. PageIndex's local mode has no retrieval-only call (`submit_query` is cloud-only and deprecated), so its retrieval is read from the agent's own timeline.

vectorless-bench's `pageindex` retriever was not used. It drives PageIndex's tree with our own single-call selector, so it measures our prompt on their tree, not PageIndex's retrieval. Filed as a follow-up.

**Vectorless.** engine-hal837 at `9b26472`, built fresh and run as its own server on :7711 with its own Postgres database and storage. It shares nothing with the live stack on :7710. Config is `.live/engine.yaml` with the port, database and storage changed, debug logging on (for Judge request traces) and `retrieval.treewalk.model: glm-4.5-air`. Per question it made three calls in a row:

- `/v1/query`, the shipped retrieval (judgewalk), sections only;
- `/v1/answer`, the shipped retrieval plus the glm-4.5-air answer, with evidence pages and a server-side retrieval/answer/pincite split;
- `/v1/answer/treewalk`, the engine's generative page walk on glm-4.5-air, the same-model analogue of PageIndex's agent.

**Caches off.** Vectorless ran with `retrieval.cache.enabled: false`. PageIndex's prompt-cache marks (`cache_control` on Anthropic-routed models) were patched off. z.ai still caches long prompt prefixes on its own side, which neither system can switch off: PageIndex read a median 40k cached input tokens per question, and treewalk 26k. That helps the generative systems, PageIndex most. The Judge's caching is not visible to us.

**Provider time vs our time.** Every glm-4.5-air call from either system went through a pass-through timing proxy (`harness/timing_proxy.py`, one instance per system). The proxy records send, first byte, last byte and reported usage. Judge requests come from the engine's own `judge: request` trace (prepare, first byte, total). For each run window, provider time is the union of provider intervals and local time is the remainder, the same split as the 2026-09-28 evaluation.

**Gold pages,** from `pdftotext -layout` per page. A page holds the answer when its text has the figure next to its label:

| question | rule | pages |
|---|---|---|
| revenue | `32,765` | 14 20 22 24 56 72 73 126 127 |
| capex | `1,577` + PP&E / capital expenditure | 39 46 49 60 126 |
| dividends | `3,193` or `$3.193 billion` + dividend | 47 48 59 60 |
| risk factors | Item 1A, which runs from p10 to Item 1B on p12 | 10 11 12 |
| operating cash flow | `6,439` or `$6.4 billion` + operating | 26 46 49 60 |
| largest segment | `12,267` + Industrial | 22 33 72 73 126 |

The answer check is a regex for the figure (any of `32,765` / `$32.8 billion` and so on), applied to the five numeric questions. Risk factors is scored on pages only.

## Ingest

| | run | ready | provider time | our time | LLM calls |
|---|---|---|---|---|---|
| Vectorless | 1 | 19.2 s | 3.7 s (Judge) | 15.5 s | 6 Judge, 0 generative |
| Vectorless | 2 | 10.5 s | 3.2 s (Judge) | 7.3 s | 6 Judge, 0 generative |
| PageIndex flash | 1 | 210.0 s | 61.0 s | 149.0 s | 142 glm-4.5-air |
| PageIndex flash | 2 | 204.4 s | 71.9 s | 132.5 s | 188 glm-4.5-air |

- **PageIndex's index time is mostly local CPU, not the model.** For the first 132–149 s no model is called. cProfile puts that time in flash's character-level PDF parser and PyPDF2 text extraction. Flash's parser is meant to run in parallel, but page 1 of this PDF uses a Type3 font. The parallel pass raises `_Type3Detected(0)` and flash re-parses all 160 pages on one core. `harness/type3_probe.py` reproduces this on its own. On a faster CPU, or a PDF without a Type3 font on any page, PageIndex would index much faster. Its README quotes 13 s to 4.5 min for 9 to 1,098 pages. Its model phase alone (61–72 s, 140–190 calls, 0.54–0.67M input tokens) is still several times our whole ingest.
- **Most of Vectorless's ingest is ours too:** 7–15 s of the 10.5–19.2 s. Run 1 includes a 1.7 s wait in the queue and a 3 s gap between parse and save. Rendering page images for pincites finished 12 s after `ready`, in the background. Production measured 13 s upload to ready today.
- **A third Vectorless ingest is excluded.** TypeSafe's credit ran out at 22:20:02 (`402 billing_error: no available TypeSafe API credits`). That was after the query run, whose 214 Judge requests all returned 200. The ingest took 125 s, because llmgate retries a 402 as an unknown error and the TOC builder then fell back to the generative path, and it still reported `ready` with a degraded tree. Raw record: `raw/vectorless-ingest-r3.json`.

## Retrieval

| 18 runs | median | p90 | provider (median) | ours (median) | LLM calls / question |
|---|---|---|---|---|---|
| Vectorless `/v1/answer` retrieval | **1.70 s** | **2.15 s** | 1.68 s | 18 ms | 5–6 Judge |
| Vectorless `/v1/query` (round trip) | 2.00 s | 2.25 s | 1.98 s | 17 ms | 4–5 Judge |
| PageIndex, to last page fetched | 7.05 s | 10.63 s | 6.79 s | 172 ms | 2–4 glm (median 2) |

- Vectorless's retrieval is almost all provider time. Judge first byte was a median 578 ms (p90 753 ms) over 192 requests. Preparation was a median 1 ms, with one 296 ms outlier.
- PageIndex's local overhead is 70–300 ms per question, plus a one-off 6.3 s before the first model call of a new process (imports, client and agent setup). That one-off lands on its first question, r0 q0, and stays in the medians above. Without that row, PageIndex retrieval is 7.04 s median and 9.20 s p90.
- PageIndex's agent spends its time on prefill. The tree outline is about 95k characters, and the page fetches run 7k–91k characters. Revenue took 4–5 calls: the agent paged through the outline twice and read 25 pages once (pp. 15–39).
- `/v1/query` is 0.3 s slower than the retrieval inside `/v1/answer`. Both make the same 4–5 retrieval Judge requests. The difference is the section bodies `/v1/query` loads and returns.

## Full answer

| 18 runs | median | p90 | LLM calls / question | pages used (median) |
|---|---|---|---|---|
| Vectorless `/v1/answer` (shipped) | **5.27 s** | **10.15 s** | 6–7 (5–6 Judge + 1 glm) | 5 evidence pages |
| PageIndex `chat` | 10.51 s | 15.84 s | 3–5 glm | 2.5 pages |
| Vectorless `/v1/answer/treewalk` (glm-4.5-air walk) | 7.64 s | 16.16 s | 4–8 glm | 2 pages |

- In Vectorless's answer, the one generative call takes a median 3.0 s (p90 7.6 s), retrieval 1.7 s and pincite selection 0.4 s. The answer call is most of the wall clock, and it grows with the length of the answer: risk factors took 9.9–14.2 s.
- Production's 3.46 s median answer is faster than this machine's 5.27 s, and the difference is in that generative call. Production's retrieval (1.76 s median, 2.61 s p90) matches this machine's (1.70 s, 2.15 s).

## Same model?

Partly. The generative model is shared: glm-4.5-air, same provider, same key, for PageIndex's indexing and chat and for Vectorless's answer and treewalk. Retrieval is not. Vectorless's shipped retrieval runs on the Judge, a non-generative model that ranks sections and pages, and PageIndex's agent needs a tool-calling chat model, so the two cannot be pointed at one model. The retrieval and full-answer rows therefore compare the two products as shipped, each on its intended retrieval model. The treewalk row is the same-model control: Vectorless's own tree and pages, walked by glm-4.5-air the way PageIndex's agent walks its tree.

## Where PageIndex wins

- **Against our same-model walk, on two of six questions.** PageIndex answered risk factors (15.2 s vs 16.2 s) and largest segment (9.5 s vs 13.2 s) faster than treewalk on glm-4.5-air. Treewalk walked 4 and 7 pages for those, and PageIndex fetched 3. Treewalk's p90 (16.2 s) is also slightly worse than PageIndex's (15.8 s). Our generative walk is not reliably faster than theirs. The lead comes from the Judge-based retrieval.
- **Fewer model calls per question:** 3 at the median against 6–7 for Vectorless's answer. Here a call count says little about latency, because five of Vectorless's calls are 0.6 s Judge requests.
- **Tighter context, sometimes:** PageIndex gives the model a median 2.5 pages against Vectorless's 5 evidence pages. It ranges from 1 page up to 25, and only half of PageIndex's pages are gold at the median, against all of Vectorless's.

It does not win on ingest, shipped retrieval or shipped full answer on this filing and this machine. Part of the ingest gap is the Type3 fallback and this laptop's CPU, not PageIndex's design. The supportable statement is that Vectorless retrieved 4× faster and answered 2× faster than open-source PageIndex on the same filing, model provider and machine. It is not faster under the same retrieval model; on that test the result is mixed.

## What this does not claim

- One filing, six questions, three repeats, one machine under background load (load average up to 11). Medians are stable across repeats, and a separate PageIndex-only run earlier the same evening gave 6.83 s median retrieval and 11.79 s median answer, close to the interleaved 7.05 s and 10.51 s.
- PageIndex Cloud, PageIndex's `mode="standard"` indexer and other chat models were not measured. Its README recommends a strong chat model, and a faster model would change its numbers.
- z.ai's implicit prompt caching was on for both generative systems and cannot be turned off. PageIndex's prefix was warm from the earlier run, which favours PageIndex.
- Answer quality is a figure regex, not a graded judgement.

## Reproduce

```bash
H=2026-10-08-pageindex-latency/harness
python $H/timing_proxy.py 7798 proxy-engine.jsonl &      # engine's glm calls
python $H/timing_proxy.py 7799 proxy-pageindex.jsonl &   # PageIndex's glm calls
$H/run-engine.sh &                                       # engine-hal837 on :7711
ZAI_KEY=… python $H/pi_run.py index results/pageindex-index.json
ENGINE_TOKEN=… python $H/vl_run.py ingest results/vectorless-ingest.json
ZAI_KEY=… ENGINE_TOKEN=… python $H/interleaved.py results/interleaved.json 3 <vectorless doc id>
python $H/analyze.py                                     # -> results/summary.json
```

The scripts carry absolute scratchpad paths from this run. Edit `S`/`H` at the top of each before rerunning.
